## Why

FSTDD 目前是**单机单人**的工作流：所有 change、Gate 确认、证据链、经验沉淀都发生在一台
机器的一个 agent 上。但实际开发形态已经是「6 个 AI agent 分布在 3 台开发机上」，它们需要
共同推进同一个代码库的变更。

当前缺失的不是「能不能并行改代码」，而是**协作的载体**：
  1. 没有任务队列与 owner 概念 —— 谁在做哪一块、做到哪一步，无人可知；
  2. 没有领取的原子性 —— 两个 agent 可能同时做同一件事，或同时改同一个文件；
  3. 没有跨机的状态可见性 —— 一台机上的进度、阻塞、失败，另一台机看不到；
  4. 没有 agent 之间的信息通道 —— 澄清、上报阻塞、请求复现只能靠人转述；
  5. 没有产出回传的规范 —— 跨机传文件容易退化成「单文件拷贝式同步」，
     造成多副本漂移（本项目在 2026-09-16 已因手工 cp 发生过两次漂移）。

与此同时，仓库里已经存在大量**可复用的协作原语**却未被利用：机器可读的 change 状态
（`.fstdd.yaml`）、父子任务模型（`batch` + `batch child`）、并行切片语义（`slices.md` 的
依赖图）、单行机器状态接口（`fstdd state --compact`）、失联检测（僵尸 change 的 7 天阈值）、
已部署的云端点与幂等部署范式、已实测的 SSH 隧道与重试推送。

本变更的目标是：**在这些既有原语之上补齐协作层**，而不是另起炉灶造一套平行系统。


## What Changes

- 【清障】收尾两个遗留的顶层活跃 change（2026-09-17-migrate-to-d-drive 已 build 完成、
2026-09-16-inbox-review-sync 停在 Gate2 之后），使批级派单所需的 Guard 分支恢复可达；
同时轮换硬编码在 `origin` URL 中的明文 GitHub PAT，并修复 Guard hook 的绝对路径问题。

- 【数据面】在云服务器建立裸仓库作为**唯一真值源**，各开发机以 git-over-ssh 访问；
master 为单写者的集成线，每个任务一条短命分支；服务器以 fast-forward-only 方式
单向镜像到 GitHub 作为备份与对外通道。GitHub 不可达不阻塞任何流转。

- 【控制面】在云服务器新增一个**轻量控制面服务**，仅监听回环地址、经 ssh 访问，
负责任务租约（原子领取）、节点心跳、agent 间消息、幂等去重。
其状态**允许丢失**，可由 git 侧的任务声明重建，因而不构成新的真值源。

- 【节点运行时】提供节点身份配置、任务领取与执行的本地闭环、基于 git worktree 的
工作隔离，以及面向 agent 的命令行入口；使「领取 → 隔离执行 → 证据回传」成为
一条可审计的固定动作。

- 【协作契约】以 skill 形式固化三种协作形态：编排（拆片派单与串行集成）、
工作者（领取执行与上报）、跨机调试（故障单与证据传递）、运维（健康与水位）。
并把「唯一真值源」与「禁止跨机文件拷贝式同步」写成硬规则。

- 【加固】在服务器侧增加一道**不依赖客户端自觉**的强制门禁，使「无 active change
不得改代码」这条宪法条款在异构 agent 平台上依然成立；并补齐磁盘水位守卫
与节点掉线处置。


### New Capabilities

- **任务分派与原子领取**：任务池公开、对等领取、领取即上锁。同一任务被并发领取时恰好一个成功，
其余收到冲突响应。任务具备 owner、租约、尝试次数与终态。

- **节点注册与在线态**：6 个 agent 以稳定 node_id 注册，具备能力标签与心跳；掉线可被检测，
其持有的租约到期后自动回收，任务回到待领状态而不丢失。

- **agent 间消息**：支持提问、回答、阻塞上报、通知、交接五类消息，可按线程与收件人拉取。
消息只承载引用（commit / 仓库内路径 / 消息 id），不内联大对象与敏感内容。

- **跨机调试载体**：以故障单承载「现象 / 复现步骤 / 环境 / 证据 / 结论」，证据以仓库内提交传递，
支持请求他机复现并把结论一般化回填经验库。

- **跨机产出回传与串行集成**：产出以提交 + 推送方式回传，集成由单一集成者逐条串行合并，
合并后重跑验证，使冲突可精确定位到具体任务。


### Modified Capabilities

- **Guard 门禁**：修复 hook 绝对路径问题；并新增服务端兜底检查，使代码路径的提交若缺少
对应的 change 证据则被拒绝 —— 这是不依赖客户端平台的强制点。

- **FSTDD CLI**：新增协作相关命令组，覆盖节点、任务、消息、故障单与自检。

- **skill 层**：新增编排 / 工作者 / 跨机调试 / 运维四个 skill，与既有四阶段 skill 衔接；
不改动既有阶段 skill 的阶段语义。

- **凭证与配置治理**：远端凭证脱离仓库配置；节点私有配置明确排除在版本控制之外并纳入自检断言。


## Success Criteria

- [ ] `.fstdd/changes/` 下不存在遗留的顶层活跃 change；批级子 change 的 Guard 放行分支可达（可用一个临时子 change 实测证明）
- [ ] `git remote -v` 输出中不含任何明文凭证；轮换后旧凭证失效
- [ ] 两台不同开发机各自成功推送一条任务分支到服务器裸库；向 master 强推被服务端拒绝
- [ ] 服务器裸库 master 与 GitHub master 的 sha 在镜像周期内收敛一致；GitHub 不可达时本地与服务器流转不受影响
- [ ] 控制面服务仅监听回环地址（端状态可验证），且其数据丢失后可由 git 侧任务声明重建
- [ ] 并发领取压测：同一任务并发 20 次领取，恰好 1 次成功、19 次冲突
- [ ] 同一幂等键重复提交返回同一结果，不产生重复副作用（覆盖 ssh 双执行场景）
- [ ] 节点掉线后租约到期自动回收，任务回到待领状态并可被其他节点领走
- [ ] 端到端闭环可复现：声明任务 → 领取 → 建隔离工作区 → 逐片 TDD → 自检 → 回传 → 串行集成
- [ ] 跨机调试闭环可复现：开故障单 → 证据提交 → 他机复现 → 结论回填经验库
- [ ] 服务端兜底门禁生效：不含 change 证据的代码路径提交被拒绝
- [ ] 四个新 skill 通过既有 skill 元数据与工程规范校验，且安装到 WorkBuddy 实际加载的目录
- [ ] 既有工程测试套件保持全绿（基线 424 passed）

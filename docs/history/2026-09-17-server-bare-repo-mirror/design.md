# FSTDD 数据面落地：服务器权威裸库 + GitHub 自动镜像 - 技术设计

## Context

### 现状

上一轮 change（`2026-09-17-distributed-task-coordination`）在 Gate 2 确认的 design 中把架构定为三层：

| 层 | 组件 | 状态 |
|---|---|---|
| L1 数据面 | 服务器 Git 裸库（唯一真值源） | ❌ **仅存在于设计文字** |
| L2 控制面 | 8788 SQLite（租约 / 心跳 / 消息） | ✅ 已部署并验证 |
| L3 节点本地 | 仓库外 worktree 隔离 | ✅ 工具已就绪（`fstdd_git.py`） |

即：**协作的控制面已建好，但没有数据面可供协作。**

### 实测事实（本变更的出发点）

```
服务器裸库        find /home/ubuntu /srv /opt -name "*.git" -type d  →  空
服务器 git        git version 2.43.0
服务器 → GitHub   ls-remote 0.084s 返回 4c1fcb1        ← 直连极快
服务器 GitHub 凭证 ssh -T git@github.com → Permission denied (publickey)
本地 vs GitHub    git rev-list --left-right --count HEAD...origin/master → 15  0
服务器磁盘        59G 46G 11G 82% /
本地 known_hosts  该服务器三条记录（ed25519/rsa/ecdsa），ECDSA 已过期并持续告警
```

### 约束

- 服务器是**公网机器**（8787 端点监听 0.0.0.0），任何落上去的凭证都按"可能泄露"对待
- 远端命令在本 agent 环境**存在执行两次**的特性 → 所有远端操作必须幂等
- 本地经内置代理访问 GitHub 不稳定（502 / schannel 中断）→ 不能把镜像依赖在本地
- 宪法：`.fstdd.yaml` 的 phase/status 只能由受控 CLI 写入；Gate 确认必须人工

## Decisions

### 1. 数据面放在服务器裸库，GitHub 降级为镜像

**方案**：服务器 `/home/ubuntu/fstdd-git/stdd-repo.git` 为唯一真值源，6 个 agent 以 git-over-ssh 访问；GitHub 只作镜像与对外通道。

**为什么**：
- 协作需要一个**不依赖任何单机**的公共真相。放在某台开发机上，该机关机即全员停摆
- 服务器是 3 台开发机的公共交汇点，且已承载 8787 / 8788
- 与上一轮 Gate 2 已确认的架构一致，不引入新决策

**备选方案及排除原因**：
- 备选 A：**以 GitHub 为真值源** —— 本地经代理访问不稳定（实测 502），把唯一真值源放在最不稳的链路上不可接受
- 备选 B：**每台机各自为源、定期互相同步** —— 必然多副本漂移；本项目 2026-09-16 已因手工 cp 发生过两次漂移，属已知失败模式
- 备选 C：**控制面 SQLite 兼作任务真值源** —— 违背上一轮已确认的"控制面状态允许丢失、可由 Git 重建"，会把可丢弃状态升格为真值源

### 2. 镜像在服务器侧执行，而非本地

**方案**：服务器裸库配置 `github` remote，由 post-receive 钩子推送。

**为什么**：
- 实测服务器直连 GitHub **0.084s**，本地经内置代理经常 502 —— 可用性差距是数量级的
- 镜像不占用任何开发机资源；agent 关机不影响同步
- 推送落点是服务器，钩子在同一台机器上执行，无跨机协调成本

**备选方案及排除原因**：
- 备选 A：**本地推 GitHub**（现状 `push_stdd_repo.sh`）—— 保留为兜底通道，但不作为主通道：网络不稳导致镜像长期滞后
- 备选 B：**GitHub Actions 反向拉取** —— 需要 Actions 基建（仓库当前无 `.github/`），且方向相反（拉取而非推送）会让"谁是源"变模糊

### 3. 镜像凭证用 Deploy Key，不用 PAT

**方案**：服务器生成专用 ed25519 密钥，通过 GitHub API 注册为该仓库的 Deploy Key（`read_only: false`）；私钥落 `/home/ubuntu/.ssh`（600），不进任何仓库。

**为什么**：
- 服务器是公网机器。**PAT 泄露 = 整个账号沦陷**（含所有仓库）
- Deploy Key 权限被限定在**单个仓库**，且可通过 API 单独吊销，不影响其他资产
- 私钥不出服务器，本地 token 也不需要复制到服务器

**备选方案及排除原因**：
- 备选 A：**把 PAT 写到服务器 credential store** —— 泄露面从"单仓库"扩大到"整个账号"，收益相同
- 备选 B：**HTTPS + PAT 内嵌 URL** —— 与备选 A 同等风险，且会像本项目 `origin` 那样把明文凭证留在配置里
- 备选 C：**GitHub App** —— 权限模型更精细，但需要 App 注册与私钥管理，对"单仓库镜像"这一需求过重

### 4. 钩子同步执行 + 非强制推送

**方案**：post-receive 在推送返回前同步完成镜像尝试（`timeout` 兜底）；使用普通 `git push`（**非** `--force`）；结果写 `mirror.log`。

**为什么**：
- **同步**：让"push 成功"蕴含"镜像已尝试"，语义清晰；异步会让 agent 误判镜像已完成
- **非强制**：GitHub 定位是镜像而非真值源。若有人在 GitHub 上直接提交，强制推送会**静默抹掉**它；失败并记录才能让异常浮出水面
- **超时兜底**：避免镜像目标不可达时钩子无限阻塞推送（对应 SC-005：GitHub 不可达不得阻塞流转）

**备选方案及排除原因**：
- 备选 A：**`--force` 保证强一致** —— 会静默覆盖远端提交，与"失败要可见"的目标冲突
- 备选 B：**后台 `nohup` 异步镜像** —— push 返回时镜像结果未知，且 SSH 断开可能杀掉子进程
- 备选 C：**定时 cron 镜像** —— 引入最长一个周期的滞后窗口，且需要额外的"是否有新提交"判断

### 5. 主机密钥告警：核对后清理，而不是跳过校验

**方案**：备份 `known_hosts` → `ssh-keyscan` 取服务器当前主机密钥 → 核对指纹 → 删除过期记录 → 写入当前记录。

**为什么**：
- 告警根因是**服务器主机密钥轮换**（现只提供 ED25519 + RSA，不再提供 ECDSA），不是中间人
- 判定依据：`ssh-keyscan` 得到的 ED25519 指纹 `SHA256:Fj27m8oNh19KQAYD8M3Vj3n4Fa6uioekiV2VmR9FQH0` 与告警中服务器声称的指纹**完全一致**；且登录成功并看到预期的文件系统内容
- 长期保留告警的代价是：**真实的主机密钥变更会被淹没在噪音里**。运维上宁可"干净 + 变更时重新核对"，也不要"永远在告警"

**备选方案及排除原因**：
- 备选 A：**永久 `StrictHostKeyChecking=no`**（现有部署脚本的做法）—— 等于关闭主机校验，把中间人风险常态化
- 备选 B：**不管告警，继续用 `-o` 绕过** —— 治标不治本，且每次连接 stderr 都是脏的，掩盖真实问题

## Architecture

```
   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
   │  开发机 A    │   │  开发机 B    │   │  开发机 C    │
   │ FSTDD001    │   │ FSTDD003    │   │ FSTDD006    │
   │ FSTDD002    │   │ FSTDD004    │   │             │
   └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
          │                 │                 │
          └───────── git-over-ssh ────────────┘
                            │
                            ▼
        ┌───────────────────────────────────────┐
        │  云服务器 43.134.236.80                │
        │                                        │
        │  /home/ubuntu/fstdd-git/stdd-repo.git  │
        │  ┌─────────────────────────────────┐   │
        │  │ L1 数据面：裸库（唯一真值源）     │   │
        │  │   refs/heads/master             │   │
        │  │   refs/tags/fstdd-v1.0.0        │   │
        │  └────────────┬────────────────────┘   │
        │               │ post-receive           │
        │               │ (Deploy Key, 非强制)    │
        │               ▼                        │
        │      git@github.com:2749817087qq/...   │
        │                                        │
        │  127.0.0.1:8788  L2 控制面（SQLite）    │
        │  0.0.0.0:8787    经验端点（隔离）        │
        └───────────────────────────────────────┘
                            │
                            │ 镜像（0.084s 直连）
                            ▼
                ┌───────────────────────┐
                │  GitHub  DKK_Fstdd    │
                │  （镜像 / 对外通道）    │
                └───────────────────────┘
```

**数据流**：agent 本地提交 → `git push server` → 落服务器裸库 → 钩子同步镜像 → GitHub。
**故障域**：GitHub 不可达 → 镜像失败并记录，裸库与各机流转不受影响。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 服务器是单点（裸库 + 控制面同机） | 接受单点以换取简单性；本地保留 `local` 裸库备份 + 每日 push；后续可加对象存储冷备 |
| Deploy Key 私钥存在服务器上，服务器被攻破即失守 | 权限限定单仓库；可经 API 单独吊销；私钥 600 且不进仓库；不使用 PAT 以免扩大泄露面 |
| 钩子同步执行会拉长 push 耗时 | `timeout 180` 兜底；镜像本身在服务器侧通常秒级 |
| 非强制推送导致 GitHub 分叉时镜像长期失败而不自知 | 失败写入 `mirror.log`；需纳入运维巡检项（后续 change 可加告警） |
| 服务器磁盘 82%（剩 11G） | 裸库实测仅 1.5M，不构成风险；水位已记录为运维检查项 |
| `known_hosts` 清理若判断失误会放行中间人 | 清理前备份；指纹经 `ssh-keyscan` 与告警声明双向核对；仅在两者一致时才更新 |
